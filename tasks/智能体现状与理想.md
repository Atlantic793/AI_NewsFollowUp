# headline-chaser 智能体：现状与理想

对照日期：2026-11-01。现状以当前服务代码为准；原始需求见 PRD/SPEC，启动和复现命令见 [README](../README.md)。

## 已落实的改动

本节更新旧版审查发现，避免把已经实现的能力继续列成缺陷。

1. **对话整理先预览、再确认。** 只接受已采集链接或主题素材中的链接；确认后才抓取页面并写笔记。链接或素材整理接口仍受计划确认和来源限制；用户手写笔记可以直接保存。
2. **对话与任务有预算。** 对话上下文估算上限 6000 token，模型调用等待上限 45 秒；采集按阶段记 24 步，另有 4 分钟时间上限。常驻进程请求预算包含排队时间，过期请求不会执行。一步是采集、清洗、聚类、分析、成稿各一次，不是每个检索词。已经搜到条目后步数或时间用尽，仍写成快照并标明停在哪一阶段。
3. **进程与凭据隔离。** 模型密钥仍从环境变量读取；启动参数检查会拒绝常见的密钥参数形式。采集进程采用环境变量白名单，不继承模型密钥、数据库凭据和 `NODE_OPTIONS`。
4. **任务状态落盘。** 重启时结合快照恢复状态；未完成任务标记为 `incomplete`，不自动重跑，对应晨报日期可保持暂停。
5. **未知意图有提示。** 无法识别的意图不会静默当作讨论；替换待确认动作时提示上一条将作废，待确认仍是单槽设计。
6. **目录发现复用运行时。** OpenCLI 2.0.2 是项目依赖；常驻采集进程批量读取命令注册表，目录缓存 24 小时，登录检测在独立短时进程中后台运行。

## 已验证范围

42 项自动化测试、类型检查、Lint、前端构建通过；真实公开 npm 源已走通主题创建、方案确认、搜索、快照和简报。133 条目录项与旧实现逐字段一致，92 条可选。目录首次读取约 644 毫秒、内存缓存读取约 1.4 毫秒，详见 [验收记录](../docs/performance/opencli-integration-20261101.json)。性能为本机测量；浏览器登录态采集和模型生成质量未在本轮实测。

## 1. 运行时与控制流

| | 现状 | 理想 |
| --- | --- | --- |
| 循环 | 没有多步智能体循环。对话是一次补全，服务按意图做一件事。采集是固定流水线：OpenCLI 搜出标题和链接 → 按日期和排除词筛选 → `fetch_pages` 读正文 → 按正文筛主题 → 写简报。 | 感知 → 推理 → 行动 → 观察可重复。每步把观察写回，直到简报合格或预算用尽。采集节点定为搜索、筛选、`fetch_pages`、写作、落盘。 |
| 规划 | 对话是单次分类（讨论、方案、调研、追踪、整理）。调研和追踪的待确认动作带检索词原句和任务说明，确认后写入主题卡再执行。没有任务单时仍用 `buildQueries`。采集步骤写死。 | 采集阶段允许边做边改：某个源失败就换备用源，而不是整条流水线只有一条路。 |
| 预算 | 对话上下文估算上限 6000 token，模型等待 45 秒。采集有 24 步和 4 分钟。一步按阶段记：采集、清洗、聚类、分析、成稿各一次。同一平台连续搜多条词仍算一次采集。已经收回条目后，步数或时间用尽仍落快照，并写明停在哪一阶段；还没有任何条目时才整次停下。单次搜索请求另有排队期限。没有实际 token 账单。 | 统一传播取消信号，记录实际 token 与费用，明确各阶段预算。 |
| 人在回路 | 对话中的方案、调研、追踪和笔记先待确认；调控按钮直接发起对应动作。删除主题有界面确认，已开启的晨报自动执行。确认前能看到这次要发出的检索词和短说明。 | 保留确认边界，写明这一次将读取和写入的内容。 |

## 2. 模型与推理

| | 现状 | 理想 |
| --- | --- | --- |
| 分工 | 一个模型做全部事：对话意图、事件分组、简报、笔记正文。环境变量指定模型和地址。 | 对话和简报用主模型。分组、字段抽取可以用更小的模型。视觉只在需要看页面版式时才上。 |
| 提示 | 每条路径各有一段系统提示：对话确认主题卡、分组、写简报、抽正文。温度是 0。调研和追踪要求模型写出检索词原句和短说明。短说明只进入写作节点，不能改平台或时间窗。 | 一份角色说明加几份任务附录。角色写清边界：不编造数字和链接，搜索命令不能由模型直接调用。 |
| 结构 | 要求 JSON 对象。服务用括号截取解析，再按字段白名单过滤平台和引用。没有 JSON Schema 校验。 | 每种意图一份 schema。缺字段或类型不对就重试一次，仍失败就告诉用户，而不是当成讨论。 |
| 思考 | 不要求模型展示推理，用户也看不到。 | 内部可以有简短依据，默认不展示。用户展开时只看到「为什么选这些源」，不看到原始思维链。 |

## 3. Tool / Function calling

| | 现状 | 理想 |
| --- | --- | --- |
| 定义 | 模型只返回意图 JSON。服务通过薄适配层向常驻进程发送搜索动作；关键词作为对象参数交给 OpenCLI 执行器。 | 搜索、写笔记、改主题卡可以是带 schema 的工具。模型填参数，服务校验。`fetch_pages` 由流水线按白名单链接调用，模型不填任意网址。 |
| 路由 | 规则路由。模型选意图，代码决定能不能执行。可搜索命令来自目录，写操作动词被排除。 | 意图仍由规则把关。具体搜哪个平台可以让模型在允许集合里选，选到集合外就丢掉。 |
| 并行 | 调度层最多两个平台在途，搜索分到两个常驻进程同时执行。同一进程内仍串行，避免上游会话状态冲突。读正文最多 4 条同时打开。登录检测使用独立进程，目录并发请求合并。 | 确认会话隔离后再提高同时搜索的进程数。 |
| 回灌 | 搜索结果进入快照，下一轮对话读取最新简报摘录和最多 20 条事件标题及链接。 | 每步观察写成短记录：命令、条数、失败原因。下一轮只带摘要，不带原始 JSON。 |
| 失败 | 单个关键词失败只丢掉这一词，该平台其余词继续，已经收回的条目留下。步数或时间用尽时，已有条目仍落快照，并指出停在哪一阶段。页面摘录失败则该条摘录为空，简报退回检索摘要。不换工具。 | `fetch_pages` 失败只重试打开，不重跑搜索，也不用别的搜索接口顶替勾选平台。模型 JSON 不合格重试一次。仍失败就指出哪一个源。 |

## 打开页面（已接入）

搜索和打开分开。OpenCLI 只负责在勾选平台上找出标题、链接、日期和检索摘要。`fetch_pages` 接在日期和排除词之后：最多 12 条白名单链接。有 `FIRECRAWL_API_KEY` 时用 Firecrawl 单页抓取拿 Markdown 主内容；否则，或抓取为空时，用本机摘录。

主题是否对得上，看正文，不单看标题。正文里没有关键词、也没有必须照看，就标成和主题对不上，不进简报。标题写了主题、正文在说别的，同样丢掉。没读到正文时，才用标题和摘要判断。超过 12 条的标成未打开，不记进「和主题对不上」。

Firecrawl 只使用 Scrape。Search、Crawl、Map、Batch、Interact、Agent、Parse、MCP 都不接。发现链接仍是用户勾过的平台。密钥不进 OpenCLI，也不进轨迹。抓取失败目前不能单独重试，要整次采集再跑。退回之后，模型仍只根据摘录写；模型失败就用检索摘要，并标明还不是原文概括。

## 任务单（已接入）

侧栏在调研或追踪时写检索词原句和短说明，确认后写入主题卡。确认主题卡、以及之后点开始调研，如果还没有原句，就按「方面 + 必须照看的主体」生成，不再单发主体或方面。正文要同时含有全部必须照看，以及至少一个不在必须照看里的关键词。信息不够时，最后一条跟进带最多 3 道选择题，每题 2 到 4 项，另有「其他」填空；点选只发送一句回复。

约定如下：

- 检索词是侧栏写好的原句，确认后直接发给已勾选平台。没有原句时，每条是一个方面加上必须照看的主体。不再单发主体或方面，也不再做主体乘主体。
- 排除词、过去 N 天、打开上限仍由代码执行。平台名不在已勾选目录里的丢掉。日期不写进 OpenCLI 命令。
- 正文是否对题，继续用主题卡上的关键词和必须照看判断。短说明不代替这道筛选。
- 一段短说明写清这次要看清什么、怎样算相关。这段只交给写简报的那次模型调用，不交给 OpenCLI，也不能变成改平台或改时间窗的自由指令。
- 搜索仍是固定流水线：搜、打开、筛选、成稿。侧栏把任务说清楚，流水线按这张单执行。不另开汇总 agent。
- 步数按阶段记，不按「平台 × 检索词」记。没有任务单时，关键词与必须照看的拼接仍可能造出重复查询，但这些查询不再各占一步。4 分钟时间上限保留。步数或时间用尽时，已经留下的条目仍写成快照，并写明停在哪一阶段。一个检索词失败只丢掉这一词。
